Doorbell: flywheel × toron

One workspace watcher wakes idle panes. Bus push → dispatcher → herdr agent.prompt → agent pulls body. The piece below is full depth because you asked for it — every gap is named with its line, why it bites, and what a durable fix looks like.

BOTTOM LINE — ONE SENTENCE
Doorbell is correct in shape, brittle in runtime: the ring rules and queue are right (ADR-0005), but the watcher is a poll loop over CLI subprocesses with no plane-S high-water, no presence, no self-restart, and a spend-once budget — so it can go deaf, re-ring history, or starve after 30 min. Fix is in-process bus subscription + persisted cursors + rolling budget + real presence — half the processes, twice the trust.
SHAPE: SOUND RUNTIME: BRITTLE EFFICIENCY: HEAVY TRUST: GAPS

WHAT'S STRONG — KEEP IT

Ring rules are crisp
doorbell.rs:38 classify()
Five classes, is_presence / is_ack_only filters, addressed_to_self gate, @pin content fallback for npub p-tags. Single function, fully unit-tested. Don't touch shape.
Queue + inject gate correct
should_inject idle|done · is_drain_transition w→idle|done
Working-pane queue, last-write-wins coalesce, drain on herdr subscribe (not poll). Matches ADR-0005 D1.6 and interrupt semantics.
Generation stamping
WatcherGen mtime+len + pid supersede main.rs:7140
Pre-fix stale watchers self-retire, stamp every wake banner so agents can tell noise from live. The 0fic fix is load-bearing — keep it.
Wake state durability
WakeState since_by_pin + last_wake `doorbell.rs:668`
Survives crash, at-least-once replay is idempotent via `[doorbell]` line. The 24h lookback on first run is the right call.
Hear-or-deaf
HearTracker 120s `doorbell.rs:518`
Inject → expect presence/kind-9 within 120s, else `doorbell: unanswered pin=`. Digest surfaces it. Right shape, wrong sensor (see gaps).
Bus pipeline is lossless
InProcessBus snapshot→delta→EOSE `in_process.rs:280`
Per-subscriber mpsc, exactly-once dedup, prune every PRUNE_INTERVAL. Publish never blocks on slow sub. Keep this invariant.

GAPS — BY PILLAR

Severity: P0 load-bearing P1 reliability P2 efficiency trust

Robustness — it can go deaf silently

P0 ×3
1. Plane-S has no persisted high-water — restart replays all historyP0
plane.rs:1337 collect_trusted every 1s + seen: HashSet<id> · doorbell.rs:677 WakeState only for plane-P
Logic: toron watch dedupes only in-process memory. Dispatcher restart (crash, heal, binary bump) clears seen and re-emits every channel/job event for the project from sqlite. The dispatcher then re-rings each as a doorbell — replay storm.
Bite: old `@BlueRidge` in a 3-month-old steer channel re-wakes the agent on every restart. Budget 3/30 starves the real new mention.
Fix: store plane-S cursor (max created_at or max event id) in WakeState alongside since_by_pin. Watch filter becomes `created_at > cursor` (or `id > cursor` if ids monotonic). On restart, emit only > cursor. Test: restart → zero injects for old history.
2. Presence never reaches HearTracker — every inject times out as unansweredP0
in_process.rs:385 ephemeral 20001 not stored · plane.rs:200 presence via presence.jsonl · doorbell watch Pubkey only from Watch lines
Logic: HearTracker expects presence 20001 OR kind-9 from npub within 120s (`doorbell.rs:518`). But presence is ephemeral — bus drops it before store, collect_trusted never returns it, and presence list is a file tail not a bus feed. So watch_pubkey only sees channel posts.
Bite: an idle agent that hears via presence publish --state working still shows doorbell: unanswered pin=… after 120s — false deaf alarm that pages the captain.
Fix: make HearTracker read presence.jsonl (the real projection) OR subscribe to live ephemeral fanout via InProcessBus::subscribe (not collect_trusted replay). Bus already fans ephemeral live — doorbell just isn't listening there.
3. Watch dies = dispatcher deaf until next human commandP0
main.rs:7165 spawn toron watch once · Bell::Died => break (`main.rs:7345`) · no in-process restart
Logic: one watch child per workspace. If it exits (panic, OOM, db lock, herdr socket hiccup), dispatcher breaks the main loop outright. Heal is only external: Resonate `heal_tick` every 60s if server reachable, else lazy on next flywheel spawn/status/doorbell.
Bite: overnight crash with no human touch = hours of deaf panes. The 1-minute supervisor is best-effort; offline or queue-full → no heal.
Fix: in-process watch restart with backoff (1s,2s,4s, cap 30s) inside __doorbell. Log to doorbell log file, expose `watch_restarts` counter in status.
4. Budget is spend-once, not rolling — long crews go deaf after 30 minP1
doorbell.rs:146 PinBudget { started_unix, prompts } · allows = elapsed < budget && prompts < max · never resets
Logic: first prompt stamps started_unix; after 30 min or 3 prompts, allows() is false forever until dispatcher restart. A 4-hour bead that gets two peer questions at +10 min and a captain nudge at +35 min drops the nudge.
Dropped rings are not queued and not reported — `take_allowed` filters after queue drain, silently discarding.
Fix: rolling window (e.g. token bucket 3 per 30 min) OR per-task budget keyed to bead id, not wall-clock since first prompt. On budget hit, queue for later + surface `budget_exhausted pin=…` in status.
5. Blocked agents never get the wake they need mostP1
doorbell.rs:61 should_inject = idle|done only · blocked never injects
Logic: doorbell queues if not idle|done. A blocked agent's peer posting a fix on the steer channel or a `request-release` grant via mail will queue, then drain only on working→idle|done — which never comes while blocked. The durable loop escalates blocked separately, but the peer-to-peer unblock path is dead.
Fix: inject into blocked too (blocked is await-signal, not "don't disturb"). Or special-case: Channel+PlanePUrgent bypass the idle gate for blocked pins.
6. Coalesce loses per-channel granularityP2
doorbell.rs:72 DoorbellQueue: BTreeMap EventClass → line · pull_hint picks one h tag
Logic: two channel mentions on different channels (steer-x and review-y) while working collapse to one line — the last h wins, first channel never hinted. Agent pulls only the hinted channel and misses the other.
Fix: queue per (EventClass, channel) or store Set<h> and hint `toron channel read h=…` for each. At least dedup per hint, not per class.

Reliability — will it be up when you need it

P1 ×4
7. inbox sweep silently skips on any failure — lost wake with no signal
main.rs:7601 Command::new("toron") · continue on spawn fail or non-zero exit
Any toron failure (daemon down, db locked, arg error) just continues. No retry, no metric, no `unanswered` change. And since_by_pin jumps to now even when raw was empty/invalid — future mail between last real high-water and now can be skipped.
Fix: advance high-water only when a valid high-water was returned. On Command failure, keep since unchanged + increment `inbox_errors` exposed in status.
8. Limit 20 truncates bursts — tail urgent mail never wakes
main.rs:7608 --limit 20 · doorbell.rs:944 inbox_high_water = max created_ts
24h lookback can hold >20 messages (storm, swarm broadcast). Only the first 20 returned are scanned for PlanePUrgent/request-release. Tail beyond 20 is invisible, but high-water still jumps to max — lost forever.
Fix: page `--limit 100` + paginate by moving since forward per page, or call mailbox directly with no limit and scan all.
9. High-water compares strings, not instants — wrongmax
doorbell.rs:963 .max() on RFC3339 strings
Lexicographic max is not chronological when formats differ (with/without fractional, Z vs +00:00). Two messages in same second with different serialization can invert. Clock skew across toron writers makes it worse.
Fix: parse to unix micros and compare numbers; store since as micros or canonical RFC3339. Use `created_ts_us` where available (InboxMessage already has it).
10. Pid liveness via kill -0 + mtime×len is forgeable
doorbell.rs:191 pid_alive kill -0 · WatcherGen mtime+len `doorbell.rs:272`
Pid reuse: a new unrelated process with same pid looks alive → false Attach. Mtime second granularity: rebuild within same second with same len → stale watcher not superseded, false wakes loop forever (the 0fic class). No flock.
Fix: flock the pid file (advisory), store pid start-time or ppid, identity = hash of binary (first 4k or sha256) not just len.
11. Supervisor only heals workspaces that already have a .gen
doorbell.rs:736 dead_dispatchers scans doorbell/*.gen only · wakeState at top-level not scanned
Fresh workspace that failed its first spawn, or a state dir migrated without .gen, never healed. Also supervisor needs a running Resonate worker to fire — offline machine never self-heals.
Fix: heal from spawn-registry workspaces (Flywheel's source of truth) plus .gen, and add a launchd/systemd fallback note for offline hosts (opt-in).
12. herdr agent.prompt fail = prompt loss, hear not marked, no retry
main.rs:7479 agent_prompt · eprintln only · doorbell_prompt returns ok list only for success
Socket hiccup while prompting = silent drop. Agent never wakes, HearTracker never arms, so no `unanswered` signal either. Double loss.
Fix: retry once with 1s backoff + surface `prompt_failures` counter; on fail, still arm HearTracker so unanswered fires.

Efficiency — why it cost 24 GB and still lags

P2
Incident: bd-741i — 100ms watch + full replay → 24GB/5h RSS, 84 swapfiles, kernel panic
13. Two poll loops doing the same sqlite scan — doubled I/O
toron watch 1s full collect_trusted rebuilds ChannelStore from all lifecycle events · doorbell inbox sweep spawns 5 toron processes per second
Now: 1s is better than 100ms, but still N Workspaces × (1 watch full-scan + P pins × toron spawn) per second. For 5 crews that's ~6 full bus replays/sec, each deserializing all kind-9s. As history grows (1k msgs) cost grows O(history) per tick.
Fix (biggest win): don't shell out. Call mailbox/bus directly in-process: one Bus::subscribe with Filter (kinds + hashtag) keeps a live channel, zero polls. Replace toron CLI spawn with mailbox.fetch_inbox / bus.subscribe. One connection, incremental.
14. Snapshot memo helps but channel post still deserializes everything
BusEventStore snapshot memo keyed by (filter, mutation version) — second identical subscribe skips scan `in_process.rs:569`
Memo hides the SQL scan, but the dispatcher still rebuilds ChannelStore from every replayed event on every spawn of watch. With long-lived watch it's once, but inbox sweep still paginates naively.
Fix: use `since` cursor on the store (WHERE created_at > cursor) so each tick reads only new rows, not full replay.
15. Main loop blocks on subprocess while watch lines queue
main.rs:7282 recv_timeout(1s) then doorbell_sweep_inbox which runs 5 sequential Command::output
Sweep holds the dispatcher thread for hundreds of ms; watch lines buffer in the mpsc channel and drain late. Under load, inject latency spikes from 10ms to 500ms. The mpsc is unbounded-ish but prompt ordering suffers.
Fix: sweep in a separate task or batch via in-process async, keep main loop only for routing (watch, status, timeout). One task = watch→inject, one task = sweep→inject.
16. Watching 7 & 20001 for rings that never ring
kinds 9,7,43001,30031,20001 watched; classify never returns for 7
Wasted filter width and wasted InboxSweeps matching. Reactions are deliver-only, presence is ephemeral anyway. Filter should be tight: 9,43001,30031 for rings + live 20001 subscription for hear only.

Trustworthiness — can you act on a wake

trust
17. Doorbell line is pull-hint, not proof — but agents may treat it as fact
doorbell.rs:966 doorbell_line "kind 9. Pull: toron channel read h=…"
Good: body stays pull (gift-wrap never pushed). Gap: hint is a suggestion; if the read races ahead of the write (watch→bus visibility 50ms), `channel read` returns empty and a naive agent concludes "nothing to do" and exits. No generation or event id in the hint to prove there is work.
Fix: include event id in hint (`Pull: toron channel read h=x --since <ts> # event id abc`). Or better: include the triggering event id set so agent can assert non-empty.
18. Spend-once budget is an untrusted DoS — any mention can burn the 3
take_allowed drops silently when prompts >=3
Any project member (or compromised agent) can `@mention` a pin 3 times and exhaust its budget early, silencing legitimate captain wake for the next 30 min. No per-sender limit, no priority (urgent vs chatter equal).
Fix: budget per (sender, class) or reserve 1 slot for captain/plane-P urgent. Log budget burns with sender.
19. p-tag is trusted after verify, but @pin content is not
doorbell.rs:822 content.contains("@BlueRidge")
Channel `p` tags are signed (verified at `publish:366`). `@pin` in content is not — anyone can write `@Victim` in a room the victim never joined and trigger a wake. Harmless today (just a pull), but if future code auto-acts on content mentions, it's an injection vector.
Fix: ring only on signed p/assignee tags; treat @pin content as advisory, not wake-worthy, or require membership for content-mention wakes.
20. No audit of doorbell decisions
HearTracker + budget + queue are in-memory only; status prints only unanswered pins
Operator cannot answer "why didn't BlueRidge wake at 14:03?" — no log of classified, queued, budget-dropped, or prompt-failed lines. The durable loop has a JSONL event log; doorbell does not.
Fix: append one JSON line per decision to `{state_dir}/doorbell/{ws}.log` (ring, class, pin, queued|injected|dropped-budget|prompt-ok|fail). Zero new deps, priceless for forensics.
21. Index npub learn is best-effort and racy
doorbell_self_index does whois per pin on 1s tick `main.rs:7408` · watch tick inserts pins with None
New pin's npub unknown for up to 1s; channel post in that window misses. Also whois fails when daemon down → index stale forever until next tick's retry. No backoff.
Fix: resolve npub on watch_targets miss immediately (single whois), not just on tick. Cache negative with TTL.

WHAT BETTER LOOKS LIKE — ONE FEASIBLE RE-DESIGN

Same ADR-0005 shape, new plumbing. No new MCP tools, no daemon→herdr socket breaking ADR-0015.

A. In-process bus, not CLI
Drop Command::new("toron") entirely. Dispatcher holds an Arc<InProcessBus> (flywheel already has the mailbox via mail_shim::mailbox() — reuse its bus). One subscribe_trusted(Filter{kinds,hashtag}) yields live events + replay via the lossless channel. No fork, no JSONL parse, no seen set reimplementing what the bus already does. Sweep becomes mailbox().fetch_inbox(FetchInbox{since_ts}) direct — no limit-20 pagination loss.
From ~6 proc/sec → 2 subs total. Latency 50ms → <5ms. RSS bomb gone (bus memo does its job once).
B. Two persisted cursors
WakeState grows one field: plane_s_cursor_us: u64 (max seen created_at or id-lexicographic). On each batch, advance cursor only after successful inject. On restart, filter is created_at > cursor — old history never re-rings. Plane-P keeps since_by_pin but stored as micros, compared numerically, and only advanced on valid high-water.
C. Rolling budget + priority
Token bucket: 3 tokens per 30 min rolling, refill continuously. Urgent plane-P borrows from captain reserve (1 token). On exhaust, don't drop — queue with budget_queued and surface doorbell: budget_queued pin=… class=…. Log every decision. Long crews stay woken.
D. Real presence + self-heal
HearTracker subscribes to live ephemeral stream (bus.subscribe for kind 20001) plus file tail as fallback. Watch restart with 1-2-4-8s backoff inside dispatcher. Pid file flocked, identity = sha256(first 8k of binary). Status shows restarts, dropped_budget, prompt_failures.
E. Tight filters
Watch only 9,43001,30031 for rings. Presence 20001 on a separate live sub for hear only. Reactions 7 not watched at all (they're presence-ish, not wake). Queue key becomes (EventClass, channel) — per-channel, not per-class.
F. Inject into blocked
Change should_inject to idle|done|blocked, or at minimum let Channel + PlanePUrgent through for blocked. Peer unblock is the whole point of the ladder — don't gate it.
